# ORGANISM — DEVELOPMENT CONTROL / AGENT GUIDANCE

## Назначение

CORE не должен парализовать разработку. Его задача — **направлять действия агента**, своевременно обнаруживать ошибки, заставлять исправлять их и использовать накопленный опыт при следующем изменении.

Формула:

**обнаружил → понял причину → исправил → проверил → продолжил**

а не:

**обнаружил → остановился навсегда**.

## 1. Обязательный принцип

Перед каждым существенным изменением агент учитывает:
- текущее зафиксированное рабочее состояние;
- архитектурные ограничения;
- известные прошлые ошибки;
- соответствующие защитные проверки;
- ожидаемый результат изменения.

Если проверка показывает ошибку:
1. определить причину;
2. исправить ошибку;
3. повторно проверить изменённую область;
4. проверить отсутствие регрессии;
5. продолжить рабочий процесс.

CORE является **навигацией и обратной связью**, а не запретом на развитие проекта.

## 2. Обязательная проверка ДО КОМПИЛЯЦИИ

Успешная компиляция не доказывает правильность программы.

Перед каждой компиляцией агент обязан выполнить предварительный review изменённой области.

### 2.1 Структура кода

Проверить:
- скобки, блоки и вложенность;
- сигнатуры методов;
- импорты;
- типы аргументов и возвращаемых значений;
- зависимости между классами/модулями;
- порядок инициализации;
- использование API в правильном контексте;
- отсутствие дублирования или случайного удаления существующей логики.

### 2.2 Алгоритмы

Проверить:
- соответствует ли алгоритм поставленной задаче;
- не нарушена ли последовательность операций;
- корректны ли условия и ветвления;
- что происходит при пустых/нулевых/отсутствующих данных;
- что происходит при ошибке;
- не возникнет ли рекурсия, цикл или повторная инициализация;
- не потеряны ли предыдущие функции;
- сохраняется ли обратная совместимость с рабочим состоянием.

### 2.3 API-контракты

Особенно проверять операции, которые компилятор может принять, но Android/API может отвергнуть во время выполнения.

Зафиксированный пример:

`SQLiteDatabase.execSQL("PRAGMA busy_timeout=5000")`

компилируется, но такой запрос нельзя бездумно выполнять через `execSQL`; соответствующий SQLite API-контракт должен быть проверен до сборки.

Следовательно, подтверждённая runtime-ошибка превращается в **предварительную проверку**, а не просто в разовое исправление.

## 3. Память ошибок

Каждая подтверждённая ошибка должна оставлять структурированный след:

**ошибка → причина → исправление → способ раннего обнаружения → защитное правило → результат повторной проверки**

Цель — чтобы следующая задача автоматически учитывала предыдущий опыт.

### Пример E-ANDROID-SQLITE-001

- Ошибка: неподходящий способ выполнения SQLite PRAGMA.
- Причина: нарушение контракта API выполнения SQL.
- Исправление: убрать ошибочный `execSQL` и использовать допустимый механизм для конкретной операции.
- Раннее обнаружение: precompile API-contract review.
- Защита: проверять все новые `execSQL/query/rawQuery` операции до сборки.
- Статус: исправлено; повторно проверять при следующих изменениях DB.

## 4. Проверка UI до выдачи APK

Для стартового экрана отдельно проверять:
- system bars / insets;
- status bar;
- navigation bar;
- первый видимый элемент;
- размеры и отступы;
- отсутствие перекрытия системными областями;
- корректность первого экрана без пользовательского действия.

Очевидная визуальная ошибка считается обычной ошибкой разработки и должна обнаруживаться до выдачи результата.

## 5. Полный цикл изменения

**Зафиксировать состояние → определить изменение → найти применимый прошлый опыт → внести изменение → проверить структуру кода → проверить алгоритм → проверить API-контракты → проверить затронутые зависимости → скомпилировать → проверить запуск → проверить основные функции → проверить регрессию → сравнить с исходным состоянием → зафиксировать новый результат и опыт.**

## 6. Правило «не считать готовым»

Нельзя считать изменение готовым только потому, что:
- файл записан;
- commit создан;
- компиляция успешна;
- APK создан.

Минимальное состояние готовности:

**структура проверена + алгоритм проверен + сборка успешна + runtime проверен + основные функции проверены + регрессия проверена.**

## 7. Роль агента

Агент должен действовать как исполнитель, использующий CORE для ориентации:

**CORE → подсказывает, что проверить и какой опыт применить → агент действует → проверяет результат → исправляет обнаруженное → продолжает.**

CORE не заменяет мышление агента и не должен превращаться в бесконечную цепь «проверки проверки проверки».

## 8. Главная догма

> **Если прошлый опыт показал, что ошибка возможна, в следующий раз соответствующая проверка должна произойти ДО того этапа, на котором ошибка проявилась.**

То есть:

**прошлая runtime-ошибка → следующая pre-runtime проверка.**

И:

> **«Собралось» ≠ «работает».**
