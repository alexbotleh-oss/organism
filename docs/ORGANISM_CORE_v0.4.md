# ORGANISM CORE v0.4 — архитектура и руководство

**Статус:** первая реализационная итерация; не production-ready.  
**Стек:** Python 3 + SQLite, без сторонних зависимостей для ядра.  
**Цель:** усилить существующий модульный прототип, не переписывая UI и мост агента одним большим изменением.

## 1. Принципы, принятые из архитектурного аудита

1. RAW/source provenance хранится отдельно от производных записей.
2. События добавляются в журнал; обычная коррекция не стирает историю.
3. Утверждение и его проверка — разные поля и разные сущности.
4. Частота повторений и согласие нескольких моделей не повышают статус проверки.
5. Опыт требует контекста, действия, наблюдаемого результата и способа проверки. Без подтверждения остаётся кандидатом.
6. Опыт по умолчанию ограничен проектом; среда и версии фильтруются при подборе.
7. Handoff является отдельным производным представлением, но точный отправленный снимок сохраняется.
8. Текст, созданный ORGANISM, помечается origin и не считается независимым свидетельством.
9. Высокорисковая задача не получает непроверенные утверждения по умолчанию.
10. Удаление выполняется только после явного разрешения пользователя; содержимое редактируется, tombstone сохраняет минимальную целостность связей.
11. CORE/policy — код и сопровождаемая документация; данные памяти не могут переписать их автоматически.
12. Проверка должна помогать исправить ошибку и продолжить работу, а не блокировать разработку бесконечной цепочкой проверок.

## 2. Модули

```text
core/organism_core/
  store.py      SQLite schema + persistence + provenance + event log + tombstones
  policy.py     deterministic admission/verification rules
  handoff.py    context selection + exact snapshot persistence
  __init__.py   public module interface
core/tests/
  test_core.py  safety-focused regression tests
```

Существующий `web/` и `organism_server.py` пока не изменяются: это снижает риск поломать уже работающий интерфейс/авторизацию, пока ядро проходит отдельную проверку.

## 3. Модель данных

- `raw_sources`: исходные тексты, SHA-256, длина, полнота импорта, время импорта.
- `events`: append-only журнал действий и изменений с actor, origin, временем события и временем регистрации.
- `assertions`: утверждения, источник/цитата, говорящий, тип, статус утверждения, отдельный статус проверки, scope, environment, версия экстрактора, временная применимость.
- `verifications`: метод проверки, класс независимости, результат и ссылка на артефакт.
- `experiences`: условия, окружение, действие, результат, способ проверки, область применимости и статус.
- `experience_applications`: выбранный опыт, задача, контекст, снимок handoff, ожидаемый/фактический исход и итог.
- `conflicts`: явные неразрешённые противоречия.
- `handoff_snapshots`: точный снимок контекста, что включено и исключено, модель и задача.
- `tombstones`: разрешённое пользователем удаление/редактирование, хеш исходного содержимого и квитанция.

Метрики (utility, harm, pollution) не хранятся как вечная истина: их следует вычислять по журналу применений/проверок.

## 4. Статусы и безопасность

Статус утверждения не равен статусу проверки. Например, `CANDIDATE + NONE` не становится проверенным от повторения текста. Внешняя проверка регистрируется отдельным событием с методом и результатом.

Допустимые сильные статусы проверки в этой итерации: `EXECUTED`, `TEST_PASSED`, `ARTIFACT_CONFIRMED`, `EXTERNAL_CONFIRMED`. Пользовательское сообщение о результате сохраняется как сообщение пользователя, но само по себе не превращается автоматически в независимую проверку.

Для high/critical задач непроверенные утверждения не попадают в handoff без явного переопределения. Даже явное переопределение не удаляет исходный статус и не переписывает историю.

## 5. Handoff

Handoff строится по проекту, задаче, окружению, классу риска и лимиту записей. Записи другого проекта не переносятся автоматически, кроме явно помеченных global-записей. При несовпадении сохранённых параметров среды запись исключается с причиной. Все исключения сохраняются в snapshot, чтобы разбирать не только то, что модель получила, но и то, что не попало в контекст.

## 6. Удаление по разрешению пользователя

Метод `authorized_delete` требует `requested_by=user|owner|data_subject`. Он создаёт tombstone, сохраняет хеш и квитанцию, очищает содержимое исходного текста или маскирует поля утверждения/опыта. Это не притворяется, что данные можно отозвать у внешнего провайдера: квитанция прямо отражает эту границу.

Перед production требуется отдельно определить удаление из резервных копий, журналов, экспортов и ранее отправленных контекстов, а также каскадную маркировку производных объектов.

## 7. Запуск тестов

Из корня репозитория:

```bash
python -m unittest discover -s core/tests -v
```

Тесты покрывают:
- запрет самоподтверждения модельного текста;
- блокировку непроверенных утверждений для high-risk;
- несовпадение окружения;
- сохранение точного handoff;
- необходимость явного разрешения на удаление и наличие tombstone.

## 9. Критерий готовности

Не считать итерацию завершённой по факту создания файлов. Нужны: unit tests, проверка схемы на чистой БД, миграционный dry-run на копии старого экспорта, regression check существующего PWA/bridge и review внешним агентом. На момент публикации этого документа тесты ещё не запускались в реальном CI; результат нельзя считать подтверждённым до их выполнения.
