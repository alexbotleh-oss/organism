# ORGANISM CORE v0.4 — архитектура и инструкция

**Статус:** первый реализационный модуль, вынесенный в отдельную ветку. Не считать интеграцию с PWA завершённой до проверки API и сквозного сценария.

## 1. Назначение

CORE v0.4 — структурированное ядро памяти и передачи контекста для уже существующего PWA-прототипа ORGANISM. Это не новая оболочка и не замена всего приложения.

Реализуемый цикл:

`RAW → PROVENANCE → CLAIM / EXPERIENCE → VERIFICATION → CONTEXT HANDOFF → MODEL → APPLICATION OUTCOME`

ИИ-модель остаётся сменным исполнителем. Она не является источником собственной проверки и не может подтвердить собственный вывод повторением.

## 2. Что уже есть в прототипе и что добавляет CORE

Существующий PWA хранит проекты, сообщения, опыт и настройки в `localStorage`. CORE добавляет отдельный Python-модуль `organism_core`, использующий стандартную библиотеку Python и SQLite. Модуль подключён к локальному серверу через отдельные `/api/core/*` endpoints. Сервер по умолчанию привязан к `127.0.0.1`; не открывать его в LAN/интернет без отдельной аутентификации и модели разрешений. PWA использует CORE Handoff при отправке сообщения и сохраняет входящие/исходящие реплики в RAW. Полная проверка сквозного сценария на реальном устройстве ещё не выполнена.

### Модули ядра

- **RAW/source** — исходный импортированный текст, SHA-256, имя источника, полнота источника и сегменты.
- **Event log** — append-only события действий ядра; UPDATE/DELETE событий запрещены триггерами SQLite.
- **Claims** — утверждения с раздельными `claim_status` и `verification_status`, происхождением, областью и окружением.
- **Verification** — способ проверки, канал, результат, описание и ссылка на артефакт.
- **Experience** — контекст + действие + наблюдаемый результат + метод проверки + область применимости.
- **Projects / states / tasks / relations** — базовые объекты для продолжения работы и миграции старого JSON.
- **User directives** — явные текущие указания с областью и необязательным сроком действия.
- **Conflicts** — явные неразрешённые противоречия.
- **Applications / Handoff snapshots** — точный JSON контекста, отправленного модели, его SHA-256, имя/версия модели и итог применения.
- **Tombstones** — журнал явного удаления/редактирования по разрешению пользователя с сохранением связей и отметкой зависимых записей для проверки.

## 3. Эпистемические правила

1. Утверждение, рекомендация, гипотеза, наблюдение и проверенный факт — не одно и то же.
2. Экстрактор не может назначить `verified` при создании записи. Для повышения статуса требуется отдельное событие `verify()`.
3. Совпадение моделей не считается внешней проверкой. Канал `model_review` не может повысить реальное утверждение до verified.
4. «Спасибо», удовлетворённость и неподтверждённый отзыв пользователя не являются внешней проверкой. Канал `user_report` не может сам по себе выставить verified.
5. Содержимое с `origin=organism_generated` исключается из Handoff как свидетельство и не может само себя верифицировать.
6. Новые/унаследованные опыты по умолчанию остаются `candidate / unverified`.
7. Проверенный опыт не переносится автоматически в несовместимое окружение. Все ключи окружения, записанные в опыте, должны совпасть с текущим окружением; отсутствие текущего значения считается неизвестностью.
8. Доверие не хранится как единый магический балл. Хранятся события проверки и статусы, по которым можно объяснить решение.
9. При применении опыта создаётся запись APPLICATION. Исход может быть `success`, `failed`, `partial`, `inapplicable`, `neutral` или `inconclusive`.
10. Опыт влияет на решение, но не становится вторым CORE и не превращается в абсолютный запрет сам по себе.

## 4. Удаление — только с явным разрешением пользователя

Операция `authorize_delete(..., authorized_by=..., reason=...)` требует непустого идентификатора уполномочившего пользователя и причины. Она:
- заменяет содержимое выбранной записи на маркер редактирования;
- сохраняет tombstone и хеш исходного содержимого;
- при удалении RAW-сегмента редактирует соответствующую строку и в полном импортированном тексте;
- помечает зависимые claims/experiences как `quarantined / needs_review`;
- добавляет событие аудита; удаляет соответствующие записи из локально сохранённых Handoff-снимков и пересчитывает их хеши, сохраняя прежний хеш в событии аудита.

Это логическое редактирование, а не обещание физического стирания всех резервных копий или данных, уже отправленных внешнему провайдеру. Для реальной политики удаления нужно отдельно учесть резервные копии, экспортированные файлы, логи провайдера и ключи шифрования.

## 5. Миграция текущего PWA JSON

Точка входа: `OrganismCore.import_legacy_snapshot(snapshot, raw_text=...)`. При передаче `raw_text` сохраняется исходный JSON-текст, включая пробелы и переносы строк; без него сохраняется сериализованный объект.

Импорт:
1. сохраняет полный JSON-снимок как RAW-источник;
2. переносит проекты, состояния проектов, задачи и связи в структурированные таблицы;
3. сохраняет каждое найденное сообщение как отдельный источник с ролью и происхождением;
4. переносит только те старые записи опыта, где отдельно присутствуют действие и результат, и помечает их `candidate / unverified`;
5. неразбираемые записи не удаляются: они остаются в полном RAW JSON; отчёт возвращает число unmapped;
6. импортированные старые события фиксируются в новом журнале как `LEGACY_EVENT_IMPORTED`.

**Важно:** это безопасная первая миграция, а не полная семантическая реконструкция. Нельзя считать старое поле `confidence` подтверждением, а старое описание опыта — доказанной причинностью. Необходимо сохранить оригинальный JSON перед миграцией.

## 6. Минимальный пример

```python
from organism_core import OrganismCore

core = OrganismCore("data/organism.db")

source = core.import_text(
    "chat.txt",
    "User: ran the test\nAssistant: try option X",
    source_kind="chat_export",
    completeness="declared_complete",
)

claim_id = core.add_claim(
    "The test passes with option X",
    project_id="PRJ001",
    source_kind="user_report",
    raw_segment_ids=source["segment_ids"],
)

# Отдельная проверка с описанием и артефактом:
core.verify(
    "claim", claim_id,
    method="pytest",
    channel="test",
    outcome="verified",
    description="Executed the named test suite; exit code 0",
    artifact_ref="test-run:2026-10-09",
)

handoff = core.build_handoff(
    project_id="PRJ001",
    task="continue the failing import fix",
    environment={"python": "3.12", "platform": "android"},
    model_name="selected-model",
    model_version="provider-version-if-known",
)

# После реального применения:
core.record_application_outcome(
    handoff["application_id"],
    outcome="partial",
    notes="Import fixed; Android runtime still not tested",
)
```

## 7. Локальный сервер и HTTP API

Запуск локального моста и CORE:

```bash
python -m pip install -r requirements.txt
python organism_server.py
```

База по умолчанию: `data/organism.db`. Путь можно переопределить переменной окружения `ORGANISM_DB_PATH`. Для файловой SQLite-базы включён WAL, внешние ключи и timeout ожидания блокировки.

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/api/core/status` | Версия ядра и количество записей |
| POST | `/api/core/import-text` | Сохранить исходный текст в RAW |
| POST | `/api/core/import-legacy` | Мигрировать существующий PWA JSON backup |
| POST | `/api/core/claim` | Создать утверждение-кандидат |
| POST | `/api/core/experience` | Создать опыт-кандидат |
| POST | `/api/core/verify` | Записать отдельное событие проверки |
| POST | `/api/core/handoff` | Сформировать и сохранить точный контекст модели |
| POST | `/api/core/application-outcome` | Записать исход применения контекста |
| POST | `/api/core/delete` | Явно разрешённое пользователем удаление/редактирование |

PWA уже отправляет чатовый запрос через CORE Handoff и сохраняет пользовательскую и модельную реплики в RAW. Ответ модели не превращается автоматически в проверенный факт или опыт. TXT импортируется в RAW; старый JSON backup можно выбрать через тот же файловый диалог.

Сервер по умолчанию привязан к loopback `127.0.0.1`. Не открывать его в LAN/интернет без отдельной аутентификации и модели разрешений.

## 8. Проверки

Автотесты находятся в `tests/test_organism_core.py`. Они покрывают:
- сохранение RAW;
- запрет самоподтверждения;
- запрет считать согласие модели или «спасибо» верификацией;
- фильтрацию Handoff по статусу и окружению;
- обязательность контекста/действия/результата у опыта;
- фиксацию результата применения;
- удаление только с явным авторизатором и причиной;
- append-only журнал событий;
- миграцию PWA JSON без повышения старого опыта до verified.

Пока CI не завершил запуск и интеграционный сценарий не проверен, нельзя утверждать, что ядро полностью готово к эксплуатации на телефоне.

## 9. Что намеренно не заявлено как готовое

- Не все действия интерфейса переведены на CORE API: старые локальные представления и экранные операции ещё требуют поэтапной интеграции.
- Нет автоматического LLM-экстрактора из больших чатов; `add_claim` и `add_experience` — контролируемые точки записи.
- Нет эмбеддингов или обязательного векторного поиска.
- Нет внешнего Ground Truth Engine для всех типов утверждений.
- Нет полноценного аудита полноты импорта ChatGPT-экспорта по message/node IDs; параметр completeness сейчас задаётся вызывающей стороной.
- Нет автоматической синхронизации окружения и версий зависимостей.
- Нет гарантированного удаления данных, уже переданных провайдерам.
- Нет подтверждённой Android/PWA end-to-end проверки, включая импорт большого TXT, передачу Handoff в модель и восстановление после перезапуска.

Эти ограничения зафиксированы намеренно: лучше точная граница реализации, чем фиктивная готовность.
