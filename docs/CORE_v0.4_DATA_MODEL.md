# ORGANISM CORE v0.4 — модель данных

Документ описывает физическую схему первого SQLite-модуля. Это рабочая минимальная схема, не окончательная онтология всего ORGANISM.

## Сущности

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `source_documents` | Исходный импортированный текст, SHA-256, полнота, метаданные | Содержит исходный payload; редактируется только в явно авторизованном процессе удаления |
| `raw_segments` | Сегменты источника с ролью, порядком, временем, происхождением и хешем | Ссылка на источник; уникальный порядковый номер в источнике |
| `events` | Append-only журнал действий и изменений | SQLite-триггеры запрещают UPDATE/DELETE |
| `projects` | Идентификаторы проектов | Идентификатор сохраняется при миграции |
| `project_states` | Снимки состояния проекта | JSON исходного состояния сохраняется для восстановления |
| `tasks` | Незавершённые и завершённые задачи | Статус и связь с проектом |
| `claims` | Утверждения, факты-кандидаты и гипотезы | `claim_status` отделён от `verification_status` |
| `claim_sources` | Происхождение утверждений | Связь claim → RAW segment |
| `verifications` | События проверки | Метод, канал, результат, описание, артефакт, актор |
| `experiences` | Условный опыт действия | Контекст, окружение, действие, исход, метод проверки, applies/fails |
| `experience_sources` | Происхождение опыта | Связь experience → RAW segment |
| `user_directives` | Явные указания пользователя | Scope, приоритет, время создания/истечения, active |
| `conflicts` | Явные противоречия | Не разрешаются голосованием моделей |
| `relations` | Ассоциативные связи между объектами | Типизированные края графа с provenance |
| `applications` | Снимок Handoff и последующий исход | Точный JSON и SHA-256, модель/версия, результат |
| `tombstones` | Записи о разрешённом удалении | Авторизатор, причина, время, хеш прежнего содержимого |

## Эпистемические статусы

### Claim

- `candidate` — извлечено, но не принято как проверенное.
- `active` — доступно как проверенное утверждение.
- `quarantined` — не использовать автоматически до пересмотра.
- `refuted` — опровергнуто.
- `redacted` — содержимое скрыто по запросу пользователя.

Проверка хранится отдельно: `unverified`, `verified`, `contradicted`, `needs_review`.

### Experience

- `candidate` — кандидат; не передаётся как доказанный опыт.
- `validated` — прошёл отдельную допустимую проверку.
- `quarantined` — требует пересмотра.
- `refuted` — опровергнут в определённом контексте.
- `redacted` — содержимое скрыто по запросу пользователя.

Переносимость не является единым свойством записи: Handoff сверяет заданные поля окружения с текущим окружением. Неизвестные значения не считаются совпадением.

## Handoff

Handoff — не отдельная база знаний. Это срез данных под конкретную задачу. В таблице `applications` сохраняются:
- task/project;
- environment;
- model name/version, если они известны;
- точный сериализованный Handoff;
- SHA-256 снимка;
- результат применения и заметки.

Запись о применении нужна, чтобы позже сопоставлять память с результатом, но один успешный случай сам по себе не доказывает причинность.

## RAW и право на удаление

Обычный импорт сохраняет полный исходный текст и его хеш. При явном разрешении пользователя операция redaction заменяет выбранное содержимое, создаёт tombstone и переводит связанные знания/опыт в карантин. Это исключение из обычной неизменяемости, инициируемое только разрешённой операцией. Событие аудита не удаляется.

## Что пока не является физической сущностью

- Единый `trust_score`: не хранится, чтобы не закреплять ложную точность.
- Консенсус моделей: не является верификацией.
- Memory Handoff cache, embeddings и поисковые индексы: производные представления, не первоисточник.
- Причинность: не выводится автоматически из последовательности сообщений.
- Глобализация опыта: автоматического повышения project → global нет.
